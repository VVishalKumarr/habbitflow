# AI timetable assistant

The **Timetable assistant** panel on the Dashboard (below the weekly timetable). It never
changes anything by itself: every change is shown first and saved only after the student
confirms.

| Part | Who | AI feature (quota) | Without AI |
|---|---|---|---|
| Command box: typed or spoken | everyone | `voice_command` | built-in parser handles the common phrasings |
| Build with AI (needs check → proposal → save) | Plus, Pro, licensed schools (`ai_guided_timetable`) | `timetable_generate` | not available; clear message |
| Check my timetable | everyone | `timetable_evaluate` (advice only) | numbers and findings still shown |
| Reschedule for an event | everyone | `reschedule` | automatic nearest-free-time plan |
| Study plan (School → Study insights) | school students | `study_plan` (explanation only) | the plan itself never needs AI |
| History and undo | everyone | — | — |

Quotas, counting and cost controls: [AI_QUOTAS.md](AI_QUOTAS.md). Help article for users:
“Timetable assistant” (`supabase/functions/_shared/help-content.ts`).

## How it fits together

```
app ──► timetable-ai (Edge Function) ──► ai_begin → Claude → ai_finish
 │            │  reads with the student's own token (RLS): timetable, my_timetable_context()
 │            └─ returns a proposal, checked by timetable-core.ts — never saves
 └─ after Confirm ──► apply_timetable_change() (one transaction, history row, undo steps)
```

- `supabase/functions/_shared/timetable-core.ts` — shared rules, used by the function, the
  app and the unit tests: proposal checking/repair, evaluation numbers and findings,
  rescheduling candidates and plan, command validation, offline command parser.
- `supabase/functions/timetable-ai/index.ts` — actions `generate`, `evaluate`,
  `reschedule`, `command`. Model `AI_MODEL` (default `claude-opus-5-5`) with a JSON schema
  answer, server-side refusal fallback, prompt caching of the instructions.
- `supabase/migrations/2026-10-16_ai_timetable_phase6.sql` — tables and functions below.
- App: `src/components/timetable-ai/*`, `src/lib/timetableAi.ts`, `src/lib/speech.ts`.

## Needs check (Build with AI)

A fixed set of questions, every one optional: goals, subjects that need more time, school
hours (only if the school timetable isn't known), fixed commitments (name, days, times),
wake/sleep, best focus time, study time per day, activities to keep/drop, anything else
(typed or spoken). The questions are part of the app, not generated by the model, so they
cost nothing and appear instantly; the model decides the timetable from the answers and
explains what it included and why (“choices”), and what couldn't fit (“impossible”).

Already known and never asked: for students of a school using HabbitFlows,
`my_timetable_context()` supplies class periods (merged into “school” blocks), homework
due in the next 3 weeks, exams and holidays in the next 6 weeks. Answers are saved in
`timetable_preferences` and filled in next time.

## Every proposal is checked before anyone sees it

`validateProposal()` removes, with a reason shown to the student:

- invalid times, slots under 10 minutes or over 4 hours, slots outside waking hours;
- slots that overlap each other (or existing slots);
- activities during school, or during a fixed commitment unless it *is* that commitment;
- two activities in the same place, more than 24 slots / 168 activities.

The result maps exactly onto the timetable model (slots shared by all days, one activity
per cell) and is saved as a **new** timetable, so nothing existing is overwritten.

## Evaluation

Computed in code, never by the model: minutes per category and per day, empty places,
unused slots, and findings — day over 6 h, 3 h+ back to back, activities after bedtime /
23:00 or before 05:00, clashes with school periods, exams within 3 weeks without matching
revision, several deadlines on a day with little study. The model only writes advice from
these numbers.

## Rescheduling

The student enters an event (label, days, times or whole day). The function finds the
displaced activities and every free cell outside the event and school; the model picks a
cell per activity from that list (anything else is ignored), otherwise the best-first plan
in `planMoves()` (same time on a nearby day, then nearest time). The student sees before →
after, can untick moves, then confirms.

Moves change the weekly (recurring) timetable — there are no one-off, single-date moves
yet. For a one-week change, undo it afterwards from History.

## Commands

The model maps one phrase to one action from a fixed list (`add_task`, `move_unfinished`,
`move_task`, `start_focus`, `mark_done`, `whats_due`, `open`, `unknown`);
`normalizeCommand()` rejects anything else. The app turns the action into concrete changes
using the current timetable and shows “I understood: …” with Confirm. Opening a page and
“what's due” don't change anything, so they don't ask.

Speech: push-to-talk microphone button. Web: the browser's Web Speech API (Chrome, Edge,
Safari). Android: `@capacitor-community/speech-recognition` (adds the `RECORD_AUDIO`
permission; asked the first time). Firefox has no speech recognition, so the mic button is
hidden and typing works. Audio never reaches HabbitFlows.

## Saving, history, undo

`apply_timetable_change(tracker, new_name, base_version, source, summary, ops)`:

- one transaction; only the caller's own personal timetables (slots/tasks are checked to
  belong to that timetable); institution timetables are separate tables and never touched;
- `base_version` must equal `timetable_version()` — a proposal made before the timetable
  was edited is refused (`STALE_TIMETABLE`) instead of overwriting the edit;
- existing checks still apply (overlapping slots, title length, categories, tracker limit);
- writes an append-only `timetable_changes` row with the steps and the steps that undo it.

`undo_timetable_change(id)` undoes the newest change only, and only if the timetable is
unchanged since (otherwise it explains why not). A generated timetable is removed by
deleting it like any other.

## Study plans (weak-subject detection)

School students get **study insights**: each subject is classified from published marks,
homework and teacher reviews by transparent rules (`compute_study_insights()` in
`supabase/migrations/2026-10-23_isolation_and_study_insights.sql`):

| Status | When (defaults; heads change them in School → Settings → Study insights) |
|---|---|
| Not enough data | fewer than 2 published marks **and** fewer than 3 homework pieces due (last 180 days) — never treated as weak |
| Needs attention | indicator < 50, or homework handed in < 60 %, or results falling (three in a row down by ≥ 10 points, or the latest ≥ 10 below the ones before) unless still ≥ 80 |
| Improving | latest result ≥ 5 points above the ones before, indicator < 80 |
| Strong | indicator ≥ 80, not falling, homework fine (needs marks, not homework alone) |
| On track | anything else |

Indicator = 80 % recent marks (last three, external exams weighted 1.5×) + 20 % homework
handed in; marks only or homework only when one is missing. Absences aren't counted as
zero. Suggested extra time per week: needs attention +120 min, improving +60, on track 0,
strong −30 (offered to weaker subjects), +60 with an exam in the next 3 weeks, +30 when
the student rates their confidence ≤ 2/5. Each subject shows its reasons. A new snapshot
(`study_insight_snapshots`) is stored whenever the underlying data changes, or every
`refresh_days`, so students and teachers can see whether a subject is improving.

`planStudyBoost()` (in `timetable-core.ts`, unit-tested in `tests/study-plan.test.mjs`)
turns the suggested minutes into changes to the student's **own** timetable:

1. general study sessions (“Study”, “Homework”, “Revision”…) get a subject — at least half
   stay general for homework;
2. a strong subject gives sessions beyond its first to a weaker one;
3. new 20–90 minute sessions go into free cells: not during school periods or fixed
   commitments, within waking hours, under the daily study limit (student's choice,
   school default 180 min), under 6 h planned per day, never making 3 h back to back, at
   most one per subject per day, spread over the least busy days.

Nothing else is ever changed: `apply_timetable_change(source => 'ai_study_plan')` refuses
any step that isn't adding a study session or re-labelling an existing study session.
What couldn't fit is explained (“Physics still needs about 1 h a week, but your daily
study limit is reached…”) instead of overloading days. Plans are previewed with a reason
per change and saved in one transaction; History undoes them.

Modes (`study_plan_settings`, per student): **off**; **recommend** (preview, then save);
**auto** — when the dashboard opens and the insights changed since the last automatic
plan (signature), the plan is applied and the student is told; undo from History.
“Explain with AI” (`timetable-ai` action `study_advice`, quota `study_plan`) adds a short
explanation and tips; it gets subject names, statuses and the planned changes — never
marks. `planAdherence()` counts how many planned sessions the student ticked (shown to
the student only).

## Class teachers

Class teachers can also edit their students' personal timetables (and their class
timetable) — see [ROLE_PERMISSIONS.md](ROLE_PERMISSIONS.md#timetables). Their edits use the
same `tt_apply_ops` steps (plus `update_task` for renaming / notes), appear in the
student's History as “Your class teacher, *name*”, notify the student and can be undone
by the student like any other change.

## Data sent to the AI provider

Only what the request needs: command text; needs-check answers; activity titles,
categories and times; for school students, class times and subject names, homework and
exam titles and dates; for study advice, subject names, their status and the planned
changes. Never names, emails, the school's name, marks or attendance. No
prompts or answers are stored (only counts and token numbers in `ai_usage`). The Privacy
Policy section “AI assistant” says the same.

  saving, transactions, stale proposals, cross-user tampering, append-only history, undo
  rules, private answers, school context isolation, function auth, plan gating, metering
  and refunds, quota refusal.
- `BASE_URL=http://localhost:5173 node --env-file=.env tests/e2e-ai-timetable.mjs` — 9
  browser steps: upgrade prompt, command → confirm → saved, mark done, what's due, check,
  reschedule → undo, focus session, needs check saved and prefilled, phone layout.

Without `ANTHROPIC_API_KEY` the tests exercise the fallbacks (model calls are refused as
`ai_not_configured` and refunded). Once the key is set, run a few real requests by hand:
build a timetable, check it, reschedule, and a handful of voice commands.
